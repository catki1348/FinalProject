## 1. 요청 사항 정리

- 별도 컨셉 이미지 없이, **이동형 발판(`MovingPlatform`) 정확히 25개만** 사용해 2-4 구간 전체를 구성합니다. 일반 발판·소멸형·점멸형·피해형·몬스터 등 다른 요소는 사용하지 않습니다.
- 기존 `MovingPlatform.cs`(speed/loopMode) + `PlatformPath.cs`(웨이포인트) 조합을 그대로 재사용합니다(1-3에서 이미 검증된 스크립트, 신규 구현 불필요).

## 2. 기존 씬 데이터 확인 결과 (Stage2.unity, 디스크 스냅샷 기준 — 실제 배치 시 재확인 필요)

- `Section_4`(2-4) 피벗은 월드 x=135. `Boundary_3_4`(x=107) ~ `Boundary_4_5`(x=149) 사이, **폭 42유닛**(카메라 스크롤 가능 범위) — 2-2와 동일한 폭.
- 현재 2-4 구간에는 다음 3개만 존재합니다(실질적으로 빈 구간):
  - `ZoneStartPoint_2-4` — 로컬 (-8, 0) = 월드 (127, 0)
  - `ZoneEndPoint_2-4` — 로컬 (8, 0) = 월드 (143, 0) — 시작점에서 16유닛 떨어져 있어 25개 발판(이동형은 스윕 공간까지 필요)을 넣기엔 많이 좁습니다.
  - `Platform_Stage2_Jungle_2-4`(일반 발판, 시작 지점 바로 아래, 로컬 -8, y=-0.525) — **"이동형 발판 25개만" 조건을 지키려면 이 기존 일반 발판은 제거**하고, 시작 지점도 첫 이동형 발판(L1) 위에 서도록 바꿔야 합니다(2-2 때와 동일한 처리).
  - `CameraBoundsZone`은 **`Section_4` 오브젝트 자신**에 붙어 있습니다(1-4/1-3처럼 별도 `Background_Forest` 자식이 아님 — 씬마다 구조가 다를 수 있으니 실제 배치 시 재확인). 현재 크기 `size=(20, 8)`, `orthographicSize=4` — 25개 이동형 발판의 스윕 범위를 담기엔 확실히 작습니다(3번 항목에서 필요 크기 계산).
  - `Boundary_3_4`~`ZoneStartPoint_2-4` 사이(월드 107~127, 20유닛)와 `ZoneEndPoint_2-4`~`Boundary_4_5` 사이(월드 143~149, 6유닛)에 아직 쓰이지 않는 여유 공간이 있습니다 — 아래 설계는 이 여유를 활용해 시작/종료 지점을 옮깁니다.
- 플레이어 이동 스펙(공통, 기존 문서들과 동일 — `Player_Warrior.prefab` 참조 확인): `moveSpeed=8`, `jumpForce=9`, `gravityScale=3` → 최고 점프 높이 ≈**1.38유닛**, 최대 수평 점프거리 ≈**4.9유닛**.
- 이동형 발판 구조: 기존 `MovingPlatform.cs`(`path`/`speed`/`loopMode`: `Loop`|`PingPong`|`Once`) + `PlatformPath.cs`(자식 Transform = 웨이포인트, 월드 좌표) 조합을 그대로 재사용. 시작 시 `rb.position`이 경로의 0번 지점으로 스냅되므로, 여러 발판이 "동시에" 움직이길 원해도 각자 자기 경로의 0번 지점에서 출발합니다(5번 병행 구간에서 활용).

## 3. 좌표 기준 및 카메라 범위 계산

- 이하 모든 좌표는 **새 시작 지점(X'=0, 아래 4번에서 `ZoneStartPoint_2-4`를 로컬 x=-19로 재배치 — 월드 116, `Boundary_3_4`에서 9유닛 뒤)을 기준으로 삼은 상대 좌표**입니다.
- 전체 설계는 X' 0 ~ 41.5(폭 41.5유닛)을 사용합니다. `Boundary_3_4`(월드107 = 기준 -9)~`Boundary_4_5`(월드149 = 기준 +33) 사이 42유닛보다 **41.5+9=50.5유닛이 필요해 8.5유닛 초과** — 1-3때처럼 `Boundary_4_5`를 뒤로 옮기는 대신, 이번엔 시작 지점 자체를 `Boundary_3_4` 쪽으로 최대한 당겨(9유닛 여유만 남김) 초과분을 줄였지만 그래도 부족합니다. **`Boundary_4_5`를 월드 149 → 157(8유닛 뒤)로 이동 필요**(구현 시 승인 후 진행, 1-3에서 구간 폭을 넓힌 것과 동일한 방식).
- `CameraBoundsZone` 필요 크기: 발판 배치는 X' 0~41.5(폭 41.5), Y' 0~9.4(9번 구간 기준 최고점) 사이에 분포 → 여유를 두어 **size=(46, 12)**, 중심은 콘텐츠 중앙(X'≈20.75, Y'≈4.7)에 오도록 `Section_4`의 로컬 위치를 재조정 필요(규칙 11). 정확한 배경 스프라이트 확대 방식(Tiled 등)은 1-3/1-4와 동일하게 실제 배치 시 처리합니다.

## 6. 수정된 수칙(13~17) 검증

### 6-1. 규칙 13 — 직선 배치는 발판 하나를 늘려서

이번 설계는 요청 조건("이동형 발판 25개만")에 따라 일반(정적) 발판을 전혀 사용하지 않습니다. 규칙 13은 "발판을 직선으로 배치할 경우 여러 개로 나누지 말고 하나를 늘려서"라는 문구상 정적 발판의 배치 방식에 대한 규칙이므로, 정적 발판이 없는 이번 설계에는 **해당 사항이 없습니다.** (참고: 1번 구간의 `L1`→`L2`처럼 같은 Y'에서 나란히 움직이는 이동형 발판이 있지만, 이는 "하나의 발판을 늘려 만들 수 있는" 정적 직선 지형이 아니라 서로 독립적으로 왕복하는 별개의 기계 장치이므로 규칙 13의 대상이 아닙니다.)

### 6-2. 규칙 14 — 발판 간 간격은 반드시 점프해야 닿는 거리

25개 전체를 이동 순서대로 나열해, 한 발판을 떠나는 지점과 다음 발판에 올라타는 지점 사이의 실제 간격(0이면 걸어서 통과 가능 = 규칙 위반)을 전수 계산했습니다.

| 이전 → 다음 | 간격 | 이전 → 다음 | 간격 | 이전 → 다음 | 간격 |
|---|---|---|---|---|---|
| ★→`L1` | (탑승 지점) | `Z2`→`Z3` | 1.2 | `O1`→`O2` | 0.3 |
| `L1`→`L2` | 1.0 | `Z3`→`Z4` | 1.2 | `O2`→`O3` | 0.3 |

| `V2`→`V3` | 1.3 | `C1`→`C2` | 0.8 | `Fi1`→`Fi2` | 0.3 |

### 6-3. 규칙 15(개정) — 설계 크기(플레이어 1초 이동거리=1 기준, 1~100 척도)

**개정된 산식**: 플레이어 캐릭터가 1초간 이동하는 거리(`moveSpeed=8` → 8유닛)를 "1"로 정의하고, 맵의 설계 크기를 이 단위로 환산해 1~100 사이 값으로 표기합니다. "설계 크기"는 기존 문서들이 일관되게 써온 "구간 폭"(시작~골인 직선 X 범위)을 기준으로 삼았습니다(참고용으로 6-2번의 누적 이동 동선도 같이 환산).

- 구간 폭(X' 0~41.5) 기준: 41.5유닛 ÷ 8유닛/초 = **5.19 → 척도 5**
- (참고) 누적 이동 동선(6-2번 계산, 탑승+점프 합계 ≈62.7유닛) 기준: 62.7 ÷ 8 = **7.84 → 척도 8**

**설계 크기: 5 / 100**(구간 폭 기준, 규칙 15 산식의 기본 해석) — 참고 수치(누적 동선 기준)로는 8/100입니다. 규칙 15가 "설계 크기"와 "이동 동선"을 구분하지 않아 어느 쪽이 의도인지 모호하지만, 어느 쪽이든 자릿수 차이 없이 한 자리~낮은 두 자리 수준이라는 결론은 같습니다. 정확한 기준은 사용자 확인 후 다른 구간에도 동일하게 소급 적용하겠습니다.

## 7. 비고 / 확인·의존성 필요 사항

1. **기존 `Platform_Stage2_Jungle_2-4`(일반 발판) 제거 필요**: 2-2와 동일한 사유로, "이동형 발판 25개만" 조건을 지키려면 삭제하고 `L1`이 시작 지점을 대신합니다.
2. **`ZoneStartPoint_2-4`/`ZoneEndPoint_2-4` 재배치 필요**: 로컬 x=-8/+8(16유닛 폭) → 새 설계 기준 각각 `Boundary_3_4` 인근(여유 9유닛)과 `Boundary_4_5` 인근으로 이동해야 25개 발판(+스윕 공간)이 들어갈 폭을 확보합니다.
3. **`Boundary_4_5` 이동 필요**: 3번 항목 계산대로 현재 위치(월드149)로는 8유닛 부족합니다. 월드 157로 이동을 권장합니다(1-3에서 구간 폭을 넓힌 전례와 동일한 처리 — 다음 구간인 2-5(보스존) 시작 위치와의 간격도 실제 배치 시 함께 확인 필요).
4. **`CameraBoundsZone` 확장 필요**(`MapEdit.md` 규칙 11): 현재 기본값(20×8)에서 (46×12)로 확장하고 중심을 콘텐츠 중앙으로 옮겨야 합니다. `Section_4` 자체에 컴포넌트가 붙어 있어 1-4(별도 `Background_Forest` 자식)와 구조가 다르므로, 실제 배치 시 어느 오브젝트를 옮길지(=Section_4 자신을 옮기면 그 자식인 시작/종료 지점 등도 함께 움직이므로 자식들의 로컬 좌표를 반대로 보정해야 함) 신중히 처리해야 합니다.
5. **배치 후 전수 겹침 검사 필수**: 1-3/2-2 선례대로, 이동형 발판은 **정지 위치가 아니라 전체 이동 스윕 범위**를 기준으로 다른 발판과 겹치지 않는지 스크립트로 검증할 예정입니다. 위 좌표는 설계 의도이며 실제 배치 시 조정될 수 있습니다.
6. **6번(루프 컨베이어) 구간의 체감 난이도**: `Loop` 모드는 이 프로젝트에서 처음 실전 배치되는 사례입니다(기존 1-3/2-2는 전부 `PingPong`). 순환 경로가 항상 한 방향으로만 진행되어 "놓치면 한 바퀴 다시 기다려야 하는" 리듬이 되는데, 이것이 의도한 난이도인지 확인 필요합니다.
7. **7번(원웨이 하강) 구간의 재도전 문제**: `Once` 모드 발판은 한 번 도착하면 멈춰서 다시 왕복하지 않습니다. 플레이어가 이 구간에서 떨어져 재도전할 경우(씬 재시작 전까지) 이미 도착 위치에 멈춰버린 발판을 다시 탈 수 있어 문제없지만, 만약 "매번 처음부터 다시 움직이길" 원하신다면 별도 리셋 로직이 필요합니다(현재 `MovingPlatform.cs`에는 없음).
8. 본 문서의 좌표/속도/폭은 설계 제안이며, 실제 배치는 Unity 작업이므로 사용자 승인 후 별도로 진행합니다(규칙 9, 11).
9. **규칙 16(맵 간 겹침 방지) 확인 결과**: 다음 구간 `Section_5`(2-5, 보스존)의 `ZoneStartPoint_2-5`는 월드 (220, -60)으로, 2-4 콘텐츠(월드 x 116~157 부근, y 0~9.4 부근)와 x로 63유닛, y로 60유닛 이상 떨어져 있어 **겹침 없음**을 확인했습니다. 다만 `Section_5`가 이렇게 멀리 y=-60에 떨어져 있는 것 자체가 아직 본 위치 조정이 안 된 상태일 가능성이 있어(2-5는 이번 설계 대상이 아니므로 손대지 않았습니다), 2-5 작업 시 별도 확인을 권장합니다.
