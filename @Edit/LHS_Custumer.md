# LHS_Custumer.md — Work Rules

Rules for how work in this project must be carried out. All entries are kept in English (rule 2).

1. Any response discussing or reviewing these rules must be given in Korean.
2. Any rule submitted in a language other than English must be simplified and stored here in English.
3. Rules are prioritized in ascending order by number — a lower rule number takes precedence over a higher one.
4. Unless an explicit exception is stated for a task, all work must follow these rules.
5. If two or more rules conflict, ask the user how to resolve it before proceeding.
6. Review these rules before starting any task. After finishing, check the resulting work against these rules; if no violation is found, the task is complete.
7. When asked to add a new rule: if no position is specified, append it at the bottom with the next number. If the user specifies a number, insert it there and shift the existing rule at that number and all after it down by one.
8. When generating an image in a workflow, enter text specifying that it be generated at 4K resolution.
9. Any work that uses Unity is carried out only after asking the user and receiving an answer. This includes all work that uses Unity in any way, such as saving or moving any object into Unity.
10. A rule prefixed with `_Unity /` applies only to work done in the Unity program; skip it when reviewing work done in any other program.
11. Do not perform any work through Unity unless explicitly instructed to work in Unity.
12. A rule prefixed with `_Blender /` applies only to work done in the Blender program; skip it when reviewing work done in any other program.
13. When working with a workflow, do not use the "Run All" action, but run the created nodes simultaneously so the work itself is processed in parallel.
14. When downloading a 3D model from VARCO, download static (non-animated) models as GLB.
15. `_Blender /` When doing work in Blender that adds something to a character, preserve the original shape of each character's model as the top priority.
16. `_Blender /` When merging a character and an animation in Blender, make sure the character's rigging and the animation's rigging match 1:1.
17. `_Blender /` When merging an animation and a character, make sure the skeleton does not stick out beyond the character (no bones visibly exposed outside the mesh).
18. When asked to generate an image or 3D model, use the connected workflow to generate it. If generation is not possible or no workflow is connected, ask the user to connect a workflow instead.
19. Name a 3D model generated by a workflow using core keywords from the text used to generate it, so the name intuitively conveys its content.
20. `_Unity /` When bringing a 3D model generated by a workflow into Unity, do not register it directly in the scene. Make it a Prefab and register it only in the `@Prefab` folder.
21. If a failure occurs during a multi-node workflow run, proceed with the other, non-failed nodes individually.
22. When a screenshot is used to check work status, delete the screenshot file completely after confirming the work, so it does not take up storage space.
23. `_Unity /` Unless otherwise requested, save Prefab files only in `@Prefab`.
24. `_Unity /` When testing is needed in Unity, create a temporary scene named like `Test000`, `Test001`, `Test002`, etc., test in it, and delete that scene once testing is finished. This rule always applies unless otherwise requested. If a scene with the same name as the test scene to be created already exists, create a new scene with a different name to test instead.
25. If a situation arises that is not covered by any rule defined here, refer to `CLAUDE.md`.
26. When asked to organize/manage a set of items, create a folder named `@[management-target-name]` for them, and save the items inside it in folders named `[management-target-name]_[number]`. Create management folders under the relevant program's folder inside `C:\Users\<현재 사용자명>\Documents\LHS` if the items are not applied to the game, or inside the project's `Assets/@ExternalAssets` folder if they are applied to the game.27. When checking the completeness of a finished result, take 5 screenshots — front, back, left, right, and top (overhead) views — to verify it.
27. When asked to generate a Preview, bring the 3D model into Blender, take 5 shots — front, back, left, right, and top (vertical) views — and combine them into a single image. The 5 images must not overlap each other. Except for the center image, the other 4 images must be placed to fit exactly into each corner of a square. Name the resulting image file using keywords from the 3D object it depicts.
28. When multiple tasks started at the same time progress at different speeds, do not try to keep their progress in sync — proceed first with whichever tasks can move faster.
29. For a work item that has been marked as discarded, delete the completed work item and do not regenerate it until a separate instruction is given for that work. For a 3D object, also delete its image-generation and 3D-model-generation nodes.
30. When asked to generate a 4-view orthographic turnaround (front/back/left/right), do not combine the 4 views into a single image — generate each view as its own separate image.
31. When generating a 3D model for a subject that has a 4-view turnaround, generate the 3D model by referencing that subject's 4-view images.
32. When a 3D object has been generated, compare its silhouette against the original's silhouette. Report failure if the match rate is below 90%, and report success if it is 90% or above.
33. When a task fails, analyze the cause of the failure and report an improvement plan for it.
34. When a Preview has been generated, copy the Unity Prefab file with the same name as the screenshot file, and save the copy in the same location as the screenshot file. Also copy every file that makes up the Prefab (such as its `.glb`) along with it.
35. `_Unity /` Architecture & Manager: Use dedicated Manager classes to centrally control common systems such as state, sound, and UI. Restrict singleton usage to Manager classes only (e.g. `GameManager.Instance`); never use singletons for regular objects such as the player or monsters. Follow the Single Responsibility Principle — one script, one role (e.g. split a Player script into Movement, Health, and Inventory scripts).
36. `_Unity /` Object Communication: Strictly forbid `GameObject.Find()`; reference objects via Inspector assignment (drag & drop) or Manager caching instead. Use event-based communication (Observer pattern) via C# `event`/`Action` to minimize coupling (e.g. Player only raises a "hit" event, and UI subscribes to it to update itself).
37. `_Unity /` Object References: Except in special cases, prefer `GetComponent`-family functions over direct Inspector assignment. Strictly forbid hierarchy-search functions such as `GameObject.Find` to avoid runtime performance loss. Avoid comparisons using strings (tags, names, etc.) to prevent performance loss and human error.
38. `_Unity /` Resources & Assets: Prioritize Prefabs — any dynamic or repeated object must be made into a Prefab; do not edit such objects directly in the scene, always edit the original in Prefab Mode. Use prefix naming rules for intuitive asset identification (e.g. `P_` for Prefab, `T_` for Texture, `M_` for Material).
39. `_Unity /` Except in special cases, do not perform dynamic object allocation in code that runs every frame, such as in `Update`.
40. When finishing any piece of work, write comments that explain what each function/feature does, so the user can pick it up and code by hand later without needing to ask.
41. `_Unity /` When any file inside `Assets` exceeds 10MB, move it into the `@ExternalAssets` folder and update every reference/path pointing to it so nothing breaks.
42. `_Unity /` Store `.md` files inside an `@Edit` folder created within the project.
43. When the command `/프로젝트 체크` is received, perform the Project.md recording task for every session in the relevant group. For each session, do not stop at checking whether an entry merely exists — compare that session's current `lastActivityAt` against the coverage timestamp already noted at the end of its entry. If `lastActivityAt` is newer than the noted coverage, the session has unrecorded follow-up activity: read its transcript from that point and add a supplement entry (do not treat an existing entry as sufficient just because the session ID appears in the file). Every entry or supplement entry — new or existing — must end with a one-line coverage marker in the form `(기록 커버리지: YYYY-MM-DDTHH:MM UTC까지)` stating the UTC timestamp of the session activity it covers, so later checks can compare against `lastActivityAt` without re-reading the full transcript of sessions that have no new activity.
44. `_Unity /` Save any script that is created inside the `@Scripts` folder.
45. `_Unity /` If a Prefab exists for an item, use that Prefab instead of the original object.
46. Git commits are made by the user personally. Do not run `git commit` (or push) on your own, even when work is finished.
47. Any rule in another document that does not follow `LHS_Custumer.md` is a violation by that document, and `LHS_Custumer.md` takes precedence.
48. Save generated artifacts of 3MB or larger inside `C:\Users\<현재 사용자명>\Documents\LHS` or the project's `Assets/@ExternalAssets` folder.
49. For backup and restore procedures, prioritize the updated documents in `G:\내 드라이브\LHS` over local copies. Ignore `LHS_Home`. If that source is unavailable, report it before using a local fallback.
50. When `/BackUpOn` is entered, restore the backed-up files and resume work from the restored session's latest unfinished task. Follow `@Edit/BACKUP_RESTORE_PROCESS.md` and the latest backup procedure from rule 49.
51. Unless the user explicitly instructs that work be applied to the main game or main work, classify and save it as concept or preview work. Apply it to the main game or main work only after such an instruction.
52. Keep LHS_Custumer and LHS_Home rules independent. When adding, modifying, or updating rules in LHS_Custumer, do not modify or update LHS_Home unless the user explicitly instructs an exception for that change. The same restriction applies in the reverse direction.
53. Preview, concept, and reference images (e.g. `GPT_Work_Room-Generate Image-*`) that end up in the `Downloads` folder are backup targets regardless of file size. Move them out of `Downloads`: if they are not applied to the game, to `C:\Users\<현재 사용자명>\Documents\LHS` (previews under `@Preview`, concepts under `컨셉`); if they are applied to the game, to the project's `Assets/@ExternalAssets` folder. Delete the originals from `Downloads` immediately after moving, without asking for confirmation. Move only files created for this project; never touch unrelated files in `Downloads`.
54. Record the AI name, model (when known), completion date, and a brief description of the work for later AI review and worker identification. Keep this attribution out of user-facing reports, rendered documents, previews, and product UI. Store it in non-rendered source comments (e.g. Markdown/HTML comments or code comments) or internal metadata. If the format cannot hold hidden attribution, use a separate internal metadata file linked to the artifact by its path or identifier. Future AI reviews must consult these records to identify who performed earlier work; never guess an unknown model.
55. When reporting work that includes animations or images, generate a preview and present it together with the report.
